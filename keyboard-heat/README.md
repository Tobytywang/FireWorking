# 键盘热度显示器

按输入活动实时显示工作热度的 Windows 桌面小工具。屏幕上常驻一个半透明的圆形仪表盘，
**把键盘击键和鼠标活动折算后并成同一个热度**，按分钟记录；随时可以打开一份单文件
HTML 报告回看历史。

```
┌─ 常驻悬浮窗 ───────────────┐      ┌─ HTML 历史报告 ──────────────────┐
│   综合活跃度数字（活跃/分）  │      │  总览（含鼠标移动/点击/滚轮/占比）  │
│   键 x · 鼠 y  ← 热度分解    │  ──  │  日历热力图（按综合活跃分级）       │
│   圆环弧长 = 热度百分比      │      │  分钟级曲线（悬停看同分钟鼠标量）   │
│   圆环颜色 = 冷蓝 → 热红     │      │  小时分布（柱内琥珀段 = 鼠标贡献）  │
└───────────────────────────┘      └─────────────────────────────────┘
```

## 快速开始

```bat
install.bat         :: ① 建运行时 .pyenv + 装 pynput（只做一次）
run.bat             :: ② 启动（Tkinter 版）
run_qt.bat          :: ② 启动（PyQt6 版，首次会自动装 PyQt6）
launch.vbs          :: 备用入口，绕开 cmd.exe（run.bat 万一不生效时用）
```

> **为什么这几个 bat 里全是英文提示？**
> cmd.exe 解析含非 ASCII 字符的 `.bat` 文件时，在部分系统上会**静默失败** ——
> 表现就是"双击了毫无反应"，而且连报错都不给。所以启动脚本刻意只写 ASCII。
> 每次执行都会把过程追加到 `_launch.log`，出问题可以事后查，不用靠猜。
> 实在不行还有 `launch.vbs`：VBScript 走 WScript.exe，完全不经过 cmd.exe。
>
> 另有一个更隐蔽的坑：工具写出的 `.bat` 默认是 **LF 行尾**，而 cmd.exe 的 `goto`
> 跳转在 LF 行尾下会静默失效 —— 脚本走到一半就没了。`_check_bat.py` 会检查并把
> 行尾转成 CRLF，改完 bat 记得跑一次。

启动后屏幕角落出现一个圆形仪表盘，**打打字或动动鼠标数字就会动**。
（启动瞬间它会先扫一圈并显示"就绪" —— 那是在向你报到。）

想先看报告长什么样，不用等攒够数据：

```bat
.pyenv\Scripts\python.exe demo_data.py --days 70
.pyenv\Scripts\python.exe main.py --report --db data/demo.db
```

报告里除了键盘 / 鼠标的热度，还会统计**每天的倒计时使用次数**：按 5 / 10 / 25 分钟
三种**类型**分别计数，并区分**触发来源**（托盘菜单 / 单击快速开始 / 双击快速开始 / 热键）。
每次「开始倒计时」记一次，选「关闭」不计入。数据落在本地的 `countdown_log` 表，
和分钟级数据同库，不联网上传。

环境自检：

```bat
.pyenv\Scripts\python.exe doctor.py
```

## 两个界面版本

`main.py` 会自动挑：装了 PyQt6 就用 PyQt6 版，否则退回 Tkinter 版。

| | `overlay.py`（PyQt6） | `overlay_tk.py`（Tkinter） |
|---|---|---|
| 依赖 | PyQt6，约 80MB | 无，标准库自带 |
| 透明 | 真·逐像素透明 | `-transparentcolor` 抠色，圆边有锯齿 |
| 操作 | 系统托盘菜单 | 全局热键 |
| 适合 | 能自由装包的机器 | IT 管控严、不想装大依赖的机器 |

Tkinter 版热键（悬浮窗完全点击穿透，收不到鼠标，所以操作全走键盘）：

| 热键 | 作用 |
|---|---|
| `Ctrl+Alt+H` | 显示 / 隐藏悬浮窗 |
| `Ctrl+Alt+R` | 打开历史报告 |
| `Ctrl+Alt+P` | 暂停 / 恢复记录 |
| `Ctrl+Alt+F` | 篝火 / 数字样式切换 |
| `Ctrl+Alt+Q` | 退出 |

> 两个版本共用同一套采集、算法和色阶，只有渲染层不同。
> 布局也刻意对齐了：状态行、大数字、单位、键/鼠分解、峰值 —— 五行的位置在两版里一致。

## 篝火模式（默认）

圆环中央是一簇**篝火**，火苗的大小和颜色都由热度驱动：

| 热度 | 火的样子 |
|---|---|
| 空闲 / 极低 | 柴堆交叉点上一团**亮橙黄**小火，芯子更亮（色阶抬到 `_IDLE_RAMP_POS` 那一档） |
| 中等 | 金黄火苗，从交叉点往四周铺开 |
| 满热 | 亮黄色大火，冒火星 |
| 暂停 | **与空闲同一个火形**（不冒火星）+ 圆环变琥珀色 |

- **暂停不改变火的形状**：`EMBER_HEAT = 0.0`。这里曾经是 0.05，而 0.05 的跨度是
  41.3px、空闲是 22.4px —— 按一下暂停火反而**变大 18.9px**，跟"火塌成余烬"正好相反
  （冷端反复提亮之后更明显：两者的色阶位置几乎一样，只剩尺寸在跳）。暂停的信号
  改由圆环的琥珀色和托盘文字承担。想要真正的"更小更暗的余烬"，得给暂停态单独
  一套尺寸/配色 —— `flame_height` 的下限就是空闲那一档，靠热度值做不到。
- **暂停时也不放火星**：`_paint_fire` 传的是 `spark_field=False` —— 哨兵必须是
  `False` 而不是 `None`，`draw_campfire_qt` 里 `None` 的意思是"没传，新建一个默认的"。

- **开屏有"点燃"动画**：火苗先窜一下再落回真实热度，替代了原来的文字报到
- **火焰锚在"起火点"上，向四周长**：形状锚在柴堆的**炭化交叉点**（不是盘底的
  火根），随热度**双向伸缩** —— 火尖往上、火根同时往下。低热时就是交叉点上的
  一小团暗红，旺起来才从这一点往上下左右一起铺开，而不是"底边固定、只往上长"。
  起火点由贴图**内容包围盒**反推（内容顶边往下 `FLAME_ANCHOR_K` = 16%，落在
  炭化密集段里）。
  它在形状里的**相对高度是反推出来的**（`flame_anchor_pos()`），不是常数：
  `pos = (火根 − 起火点) / 满热跨度`，于是柴堆换大换小都同时满足两条不变量 ——
  起火点永远在炭化交叉点上，**满热时火根永远落在火根线上**（满热形态用户验收过，
  不能变形）。早先这个比例写死 0.36，等于把"柴堆宽 0.62d"当通例：柴堆一缩小
  （0.62 → 0.53d）起火点跟着下移，满热火根就戳到柴堆底边以下、底边后面空了 ——
  被 `_logpile_preview.py` 的逐行轮廓判定抓到，`_test_flame.py` 里也补了断言
- **空闲火苗不能太小**（`flame.FLAME_IDLE_K` = 0.19）：它是空闲态**唯一**的火，
  0.09 时柴堆显得太大、火只有一小撮，整簇不协调。0.19 约是柴堆内容高的 45%。
  改完跑 `python _before_after.py` 出「旧素材+旧参数 / 新素材+旧参数 / 新素材+
  新参数」三栏对照，一眼看出变化来自素材还是参数
- **火焰本体要够亮**（用户前后提了四次："太不明显了" → "再亮一些" → "还是可以再亮
  一些" → "亮度还是不太行"）。先把色阶表拿出来看：起点 `_ramp(0)` 是 `(49,0,0)`
  —— 900K 的余烬经 T⁴ 辐射 + Reinhard 算出来就是它，物理上没错（余烬本来就几乎不
  发光），铺在深色灶膛底上却读不出在烧。而色阶上 0.75 处明明有 lum 159 的亮橙。
  所以冷态一共做了**五件事**，全部只在低热端生效、满热逐像素不变：

  | 旋钮 | 作用 | 现值 |
  |---|---|---|
  | `flame._IDLE_RAMP_POS` | 空闲取色阶哪一档（**亮度的主杠杆**） | `0.74` → `(217,151,19)` |
  | `flame._IDLE_RAMP_FALLOFF` | 上面这个抬升的衰减指数（**和 K 是一对**） | `1.28` |
  | `flame._COLD_SHADE_MIN_K` | 纵向渐变"根亮→尖暗"残留多少压暗量 | `0.13`（只压一成三） |
  | `flame._EDGE_MIX_COLD_RELIEF` | 外焰往暗红压的冷态豁免量 | `0.41` |
  | `flame._GRAD_TIP_COLD_RELIEF` | **渐变转折点**冷态往上推多少 | `0.32` → 转折点 0.55→0.87 |
  | `flame._CORE_HUE_BUMP` | 焰芯沿色阶再往上走多少（提亮**不掉饱和**） | `0.18` |
  | `flame._L12_HOT` | 第 1/2 层提亮幅度的**热度权重**指数（冷端 0、满热 1） | `0.60` |
  | `flame._L1_EDGE` | 外焰少混「暗红」的量（走**更黄**那条路，亮度与饱和同向） | `0.16` |
  | `flame._L1_KEEP_UP` | 外焰满热时顶端保留比例 +多少 | `0.20` → 0.48→0.68 |
  | `flame._L2_HUE` | 中焰底端色沿色阶再往上走多少 | `0.09` |
  | `flame._L2_KEEP_UP` | 中焰满热时顶端保留比例 +多少 | `0.08` → 0.70→0.78 |
  | `flame._CORE_TINT` | 焰芯混白的那个「白」本身（**暖白 vs 中性白**） | `(255,238,186)` |
  | `flame._L3_KEEP_UP` | 焰芯满热时顶端保留比例 +多少（**原来比中焰还低是历史遗留**） | `0.24` → 0.52→0.76 |
  | `flame._L1_TK_KEEP_UP` / `flame._L2_TK_MIX_UP` | **Tk 版**的等效提亮（Tk 画不了纵向渐变） | `0.10` / `0.18` |

  两个新旋钮都是这一轮先量后调量出来的：

  - **渐变转折点**：每层是一条"根部色 →（0.55 处）尖端色"的纵向渐变。但空闲时
    火焰只有 22px 高、下半段还被前景柴堆挡住（实测前景柴堆内容顶边 y=115，而空闲
    主火 `root_y=117.5`、`tip_y=95.1`）—— **可见的只有渐变的 0.11~1.0 段**，也就是
    有一半吃的是最暗的那档。把转折点推到 0.87，露出来的那段基本回到根部色了。
  - **焰芯加温**：让芯子沿色阶往上走，而不是**往白里混**。混白掉饱和度（早先那块
    "灰水滴" `(111,75,67)` 就是这么来的，R-B 只有 44）；沿色阶走的是亮度和色温，
    `(231,193,69)` 的 R-B 还有 162。火该有的"亮"是后者。

  调参链路：`python _flame_lum_probe.py` —— 一屏放 4 组旋钮 × 3 档热度，用
  **帧差**取"露出来的火焰像素"掩码（同一帧渲两次，第二次关掉主火层和底火层，两帧
  不同的像素才是火焰贡献的），逐格打中位/p90/最高亮度；顺带验 h100 逐像素不变。
  `_flame_lum_zoom.png` 是 idle 的 6 倍放大对照。

  ⚠ **K 和 n 是一对，动 K 必须回头看 n。** 重映射是 `t + K(1-t)^n`，在 t=0 处导数
  为 `1-nK`；一旦为负，曲线先往下走再掉头 —— "刚打几个字火反而变暗"。所以
  **`n ≤ 1/K` 是硬约束**（K=0.74 → n ≤ 1.35）。K 从 0.52 加到 0.74 时，上一版的
  指数 3 会让低谷掉到色阶 0.546（对比空闲 160 是**跌 33%**，眼睛看得出来），
  所以一并收到 1.28。
  ⚠ **代价：中低热的颜色也被一起抬上去了**（t=0.5 从色阶 0.565 → 0.758）。这是
  数学必然 —— 单调曲线在 t=0 高、在 t=1 回到 1，中间压不回原样。热的层次感改由
  **火苗尺寸**承担（空闲 22px / h50 80px / 满热 118px），测试里把"中热色阶几乎不动"
  换成了"整段单调不降 + 旺火色阶留白 ≥ 0.15"。

  ### 第 1/2 层（外焰 / 中焰）的单独提亮

  用户："亮度还是不太好 … 单独提升下前面的第一层和第二层的亮度，更白更黄。"
  先量后调（`python _layer_lift_probe.py`）—— **外焰是唯一一层「越旺越暗」的**，
  逐层帧差掩码取"这一层真正露出来的像素"，lum 中位：

  | 热度 | 第 1 层 外焰 | 第 2 层 中焰 | 第 3 层 焰芯 |
  |---|---|---|---|
  | 空闲 | 141 | 170 | 185 |
  | h19 | 94 | 144 | 159 |
  | h50 | **75** | 134 | 142 |
  | h100 | **86** | 152 | 141 |

  真因不是"没提"，而是**压暗量的折扣方向反了**：`flame_shade_k` 冷态只保留 13%
  （怕矮火焰整团发黑），满热却是 100% —— 旺火的外焰被压满，连根部色都保不住。
  而外焰占了 h100 火焰面积的 **6402 / 12900 ≈ 一半**，用户看到的"土黄发闷"就是它。

  **空闲那团火不欠亮**（141 / 170 / 185；层次差 29 是它唯一的体积线索），所以提亮
  按 `_l12_weight = heat ** 0.60` **随热度加权**：冷端严格 0 —— 四档候选里空闲列
  逐格数字全是 `+0`、颜色逐像素相同；h50 吃到 0.66、h100 吃满。

  效果（h100 外焰）：lum **86 → 129**（+50%），R−B **60 → 88**。亮度和饱和度
  **同向上抬**，因为走的是"少混暗红"（`_L1_EDGE`）而不是"混白"——混白那条路 R−B
  会掉，就是上上版「灰水滴」的老毛病。

  `_layer_lift_zoom.png` 是 h50 / h100 的 5 倍放大对照；`_layer_lift_probe.png` 是
  4 档候选 × 4 档热度全表。⚠ `_L1_EDGE` 会让 `flame_colors(1.0)` 的第一个分量变亮
  —— 这是**刻意**的，所以旧断言「满热焰芯仍是验收过的那一档」那个三元组比较已拆成
  三条性质断言：中焰/焰芯逐位不变、外焰更亮、且外焰仍比中焰暗（体积线索不许丢）。

  效果可以直接量：`python _idle_levels.py` 出「上轮 / 本轮」两栏对照图 ×
  idle / h05 / **h50** 三行（h50 是反证，证明中热没被带偏：中位 321 → 326），
  每格底下打了火焰可见区的中位/最高亮度和 —— 空闲 **136 → 242**，低热 158 → 233

  ### 第 3 层（焰芯）的调暖与提亮

  用户："最前面那层火焰, 我觉得它颜色有点'绿', 可以把它调成更加偏向黄+白的颜色吗?"

  **先破一个直觉：黑体色阶里没有绿。** 色阶 H 一路从 0° 走到 47.2°、全程 R > G > B
  （`_layer_hue_probe.py` 的 A 节把 9 个 stop 全打出来）。所以「绿」不是某个像素真的
  G > R，而是**同时对比**：一块低饱和的灰米色被全饱和的橙黄包围就会被推成"偏冷"，
  而在这簇火的语境里"偏冷"正好落在黄绿侧。

  逐层量（`python _core_hue_probe.py`，帧差掩码取每层**真正露出来**的像素）：

  | 热度 | 第 1 层 外焰 | 第 2 层 中焰 | 第 3 层 焰芯 |
  |---|---|---|---|
  | 空闲 | R−G 58 / V 76.9 | 50 / 86.3 | 37 / **88.2** |
  | h19 | 41 / 57.3 | 44 / **77.6** | 25 / 72.5 |
  | h50 | 33 / 51.8 | 34 / **73.7** | **14** / 61.6 |
  | h100 | 22 / 59.6 | 23 / **75.3** | **8** / 59.6 |

  两件事一起露出来：

  1. **焰芯的 R−G 是三层里最低的**（h100 只有 8 —— R 和 G 几乎相等，就是灰）。
     「绿」的所在是它，不是外焰。
  2. **焰芯的 V 也不是最亮**（h100 59.6，比中焰的 75.3 低 16 点）。空闲时它最亮
     （88.2），旺起来反而掉成最暗的一层 —— **层次倒挂**。上一轮提亮只挑了外焰/中焰
     （按 `_l12_weight` 加权），焰芯没动，于是被反超。

  真因有两个，各对一个旋钮：

  - **`_CORE_TINT = (255,250,224)` 是中性白**（R−G 只有 5、S 只有 12%）。按 0.70
    混进去，把色阶顶端的 R−G 从 29（12.3% of R）冲成 12（4.8%）—— 暖意被稀释
    2.5 倍。它在 `flame_colors` 里只有**一个**使用点，改这一个常量就够了；而且
    `_core_gain(0) = 0` → 空闲档混白比例是 0 → **改它对空闲那团火零影响**。
  - **`grads[2]` 的顶端保留比例硬编码 `0.52`**，比中焰的 0.78 还低。**这是历史
    遗留**：写它的时候上面两层还没单独提亮过，焰芯靠混白自己就够亮。

  改动：`_CORE_TINT` → `(255,238,186)`（暖白，R−G 17）；新增
  `_L3_KEEP` / `_L3_KEEP_UP`（`0.52 + 0.24 × _l12_weight` → 满热 0.76）。
  0.24 是**扫出来的下限**不是拍的 —— 焰芯要重新成为最亮层，V 得越过中焰的 75.3：
  `+0.00 → 59.6`、`+0.12 → 68.6`（仍比中焰暗）、`+0.24 → 78.0`（反超，S 仍只 32%）、
  `+0.36 → 87.8`（过曝成一块奶油色）。

  效果（h100 焰芯）：`rgb(152,144,115)` → `rgb(199,184,135)` ——
  **R−G 8 → 15（暖意近翻倍）、V 59.6 → 78.0（+31%）、H 47.0 → 45.9（更暖）**，
  并**重新成为三层里最亮的一层**。外焰/中焰逐像素不变、空闲档逐像素不变。

  Tk 版原来往**纯白** `(255,255,255)` 混 —— 跟 Qt 的中性白犯同一个毛病，一并改成
  `flame._CORE_TINT`。Tk 没有 `_L3_KEEP_UP` 这一档：它的焰芯是实色 `core`（V≈98），
  本来就处在"提亮之后"的状态，没有可提的顶端。

  交付图：`_core_hue_zoom.png`（h100 的 6 倍放大）、`_core_hue_probe.png`

  直接往白里混（会灰），冷态改用固定的暖芯色 `_FLOOR_COLD_CORE`。两端数值都在

  底边**才成立，0.41 是逐行轮廓判定（`_logpile_preview.py`）算出的下限，再小一档

「停靠位置」「底盘透明度」「倒计时」「单击效果」「双击效果」都是**单选**：一组里永远只有一个对号。这里有个
Qt 的坑 —— **`setCheckable(True)` 本身不带任何互斥**，同一个菜单里放几个
checkable action，Qt 不会自动把它们凑成一组，点新的一项时旧的对号会留着不放
（就是"0% 和 100% 前面同时有对号"那个 bug）。互斥只能靠 `QActionGroup`，所以
这五组统一由 `overlay.build_choice_menu` 建（里面配了 exclusive 的组），改完
再按配置值回写一遍（`_sync_tray_checks`，配置值是勾选的唯一数据源）。
**新增单选菜单一律走 `build_choice_menu`，别手写 `setCheckable`。**
回归在 `_test_tray.py`：鼠标点击与键盘回车两条真实路径都验，外加源码守卫。

菜单这一项**叫「透明度」、不叫「不透明度」**（用户第 8 轮：带"不"是否定、理解费劲），
且显示值和内部值**反相**：菜单里的 `透明度%` = `100 − bg_alpha×100`，所以
**100% 字面义就是完全透明**（与"100%"配合直观），`0%` 是实心。内部 `bg_alpha`
（不透明度）一个字没动，渲染逻辑不牵动。档位是原「不透明度 72/45/0」那三档的反相
（透明度 28/55/100），沿用已经验过的盘体观感。配置里若不是档位值，
`_snap_alpha` 会吸附到最近档，保证菜单永远有一个对号（`_test_tray.py` 第 4b 节盯）。

## 热度怎么算

原始信号是"最近 60 秒内的**等效活动量**"（键盘击键 + 鼠标折算）。这数字抖得没法看 ——
打一句话是 400，停下来想 5 秒就掉到 0。所以做了三层处理：

```
weight  = 1×击键 + 4×点击 + 2×滚轮格 + 0.01×鼠标移动      # 折算成"等效击键数"
raw     = 最近 60 秒内 weight 之和 × 60/60               # 滑动窗口，把瞬时抖动摊平
ema     = ema·(1-α) + raw·α                              # α=0.2，约等于 5 秒时间常数
heat    = min(ema / full_kpm, 1) × 100                    # 归一化到 0~100
idle    : 键鼠都停 30 秒后，heat 每秒 × 0.9               # 指数冷却，不是硬切 0
```

**热度有个下限（`heatcore._HEAT_FLOOR = 0.05`），但它只在「空闲衰减」那一支生效 ——
位置写错会造出一个死区。** EMA 从 0 起步时，每帧的增量是 `target × weight`，而每帧
都从 0 重新算 —— 增量一次达不到下限，就永远卡在 0。篝火模式是 80ms 一帧
（`weight ≈ 0.0177`），于是阈值落在 `300 × 0.5/0.0177 ≈ 85 kpm`：

| 打字强度 | 改前：起步时刻 | 改前：单帧最大跳 | 本轮：起步时刻 | 本轮：单帧最大跳 |
|---|---|---|---|---|
| 40 kpm | **从不**（打满 120 秒火纹丝不动） | 0 | 1.4s | 0.66px |
| 80 kpm | **从不** | 0 | 0.7s | 0.66px |
| 90 kpm | 56.6s | **5.46px** | 0.6s | 0.66px |
| 200 kpm | 25.4s | **5.46px** | 0.2s | 0.66px |

（实测脚本 `_smooth_probe.py`：真实 `HeatEngine` + 假时钟，固定 kpm 打 120 秒。）
用户看到的"火从小到大的过程里有个突变"就是这张表：**低于阈值时火完全没反应，
高于阈值时几十秒后一步跳 5.5px**（火苗总高只有 22.4px，那是 24%）。

同一条链上还有个放大器：跨度对热度是 `热度^0.54`（`fire_heat` 的 0.75 次幂叠
`flame_height` 的 0.72 次幂），**冷端比中段陡 7 倍**，所以任何"起步时的跳"都会被放大。
这是刻意的（小火变大最容易察觉），不是 bug —— 但正因为陡，量化精度要跟上：
快照的 `heat` 是 2 位小数（0.1 的话，起步那一步就有 2.4px 的尺寸台阶）。

**鼠标为什么要折算**：鼠标移动事件密集得离谱（指针每过一个像素就触发一次，轻松上千
每秒）。直接把事件数叠加会把热度顶死，所以给每一类定一个"等效击键数"权值：

| 事件 | 折算系数 | 理由 |
|---|---|---|
| 键盘击键 | 1.0 | 基准 |
| 鼠标点击 | 4.0 | 一次点击的心理操作量接近敲几个字 |
| 滚轮 | 2.0 / 格 | 介于点击和移动之间 |
| 鼠标移动 | 0.01 | 约 100 次移动 = 1 次击键 |

想调：`config.json` 的 `heat.w_click` / `w_scroll` / `w_move`。

界面上用**两个通道冗余表达**同一个量：弧长是热度百分比，弧色是同一数值对应的色阶
（冷蓝 → 青绿 → 草绿 → 琥珀 → 橙 → 红）。扫一眼就能读，不用盯着数字。

弧长的"空闲段下限"用的是 `IDLE_ARC_DEG / SWEEP_DEG` 这个**比例**，不是某个小常数 ——
早先写的是 `0.002`，于是热度刚从 0 升到 0.2% 时，弧长会从 2.5° **缩到 1.3°** 再重新
长起来：热度升、弧反而变短，是个非单调的小跳变（两版 UI 都有，见 `_test_flame.py` 的 9d）。

默认 300 活跃/分记作满热。打字比我快的就把 `heat.full_kpm` 调大。

状态标签有五种含义：

| 标签 | 含义 |
|---|---|
| 输出中 | 最近 30 秒打过字（`typing`） |
| 操作中 | 最近 30 秒只在动鼠标，没打字（`pointing`） |
| 停顿 | 键鼠都停下不到 2 分钟（`pause`） |
| 空闲 | 完全停手 2 分钟以上（`idle`） |
| 已暂停 | 手动按了暂停（`paused`） |

## 配置

`config.json` 里带 `*` 的字段是常用调参项，改完重启生效：

```jsonc
"heat":    { "full_kpm": 300, "ema_alpha": 0.2, "w_click": 4, "w_move": 0.01 },
"mouse":   { "enabled": true },
"overlay": { "size": 190, "position": "bottom-right", "bg_alpha": 0.88, "theme": "dark", "campfire": true, "log_style": "charred", "log_image": "assets/log-pile.png", "log_image_front": "assets/log-pile-front.png", "flame_floor": true }
```

- 觉得数字反应太慢 → `ema_alpha` 调到 0.35
- **觉得圆盘看不清 → `theme` 换成 `light`**（白底盘，深色终端/壁纸上对比度最强）。
  反过来，浅色桌面用 `dark`。圆环本身不用操心：轨道和进度弧都是**定色不透明**的，
  任何桌面、任何 `bg_alpha` 下对比度都一样（原因见下面那条）
- **底盘最外圈那道 2px 描边（`THEMES.rim`）已经去掉**（用户报"圈圈最外面有一个
  白色的圆形线条"）。它正好压在盘面半径上：dark 主题下盘内 lum 27、那圈线 135
  （Δ+108），浅色桌面下 Δ 能到 +159 —— 是一圈比火还抢眼的线。**代价说清楚**：
  dark 的盘面 (24,27,35) 和深色终端桌面本来就只差一点，去掉线之后圆盘的外沿不再
  有硬边界，两者基本连成一片（圆环、灶膛、篝火都还在，只是"圆盘"这个形状淡出）。
  想要轮廓感就换 `theme: light`，或把 `THEMES.dark.plate` 往亮里调一两档。
  逐组合实测与放大对照见 `_rim_off_probe.py` → `_rim_off_probe.png`；
  `_test_ring.py` 第 5 节盯着它不许回来。
  **注意别和下面那条搞混**：同一个"边沿"的设计后来被**挪到进度条自己身上**了
  （`THEMES.track_edge`）—— 那是因为用户要"进度条和盘面分得开"，不是要把盘子
  轮廓画回来。两条线半径差 ~6px，一条都不许少
- **进度条（圆环上那条带子）和圆盘底色分不开？** 那是**另一个**撞车，跟上面
  "弧 vs 轨道"不是一回事。轨道是定色了，可**底盘还是半透明的**、会跟着桌面漂：
  dark 主题 + `bg_alpha` 72% 撞浅色桌面时底盘到 lum 84.8，和轨道（81.4）几乎
  重合（Δlum −3.9 / ΔRGB 10.7），整块盘看着就是一片均匀的灰；light 主题 +
  72% 撞深/中灰桌面同理（Δlum +8.3 / −1.6）。解法是**把整条环带描一圈**
  （`THEMES.track_edge`，dark `#C4CBD8` / light `#5F6674`，宽 `flame.ring_edge_w`），
  把进度条的边界立起来。几个刻意的选择：① **四条边都要**（外弧 + 内弧 + 两个端头
  半圆）—— 只描外沿的话环带的内侧和弧的端头还是虚的，看着像半条边（用户第 6 轮
  报的就是这个）；② 画在轨道**之前**（Qt 靠绘制顺序、Tk 靠 `create_arc` 顺序），
  后画的轨道压在它上面。端头用**半圆**包住轨道的圆笔帽
  （`ring_edge_cap_radius` = `thick/2 + edge_w/2`），半径正好接上内外两条弧；
  灶膛（`CAMP_PIT`）必须比轮廓**更早**画，否则会把内弧切掉半条（实测可见宽度
  2.1px → 1.5px，一个纯色像素都挤不出来）。
  逐组合实测见 `_ring_frame_probe.py` → `_ring_frame_probe.png`（改前/改后 + 三处
  放大对照）；`_test_ring.py` 第 6~9 节盯着它
- **这条线的透明度是反相的**（用户第 7 轮："它的透明度和整体的透明度是反着来的"）：
  `flame.track_edge_alpha(bg_alpha)` = **`1 − bg_alpha`** —— 底盘全不透明（100%，盘面
  自己就和轨道差 54）时线**完全消失**，底盘全透明（0%，环带直接压在桌面上）时线**画满**。
  这个反相不只是照办，它正好把线留在被需要的那几档：线淡下去和"盘面自己站起来"
  是同一枚硬币的两面。**代价说清楚**：α=72% 时线只有 28% 不透明，只能把两种颜色
  拉开约 1/4 的距离（light 主题撞车档实测分离度 25，定色线是 117），所以判据是
  **max(盘面自己 vs 轨道, 线自己的分离度)**，不是"线够不够亮"。嫌中段太淡就调
  `flame.TRACK_EDGE_ALPHA_GAMMA`（<1 只抬中段，`0^γ=0`/`1^γ=1` 两个端点一动不动；
  γ=0.75 时 72% 档的线不透明 28% → 38%，最差分离度 25 → 34）。逐档实测、曲线图和
  γ 对照见 `_edge_alpha_probe.py` → `_edge_alpha_probe.png`；`_test_ring.py` 第 10 节
  盯着端点、单调性和"α=72% 的像素必须等于线色 × 28% + 底盘合成色"
- 想让它更"隐形" → `bg_alpha` 调到 0：底盘整个透明，只剩圆环、灶膛和篝火。
  圆环**不受** `bg_alpha` 影响 —— 轨道是定色不透明的，所以进度条和低热度的弧在任何
  背景上都读得出来（**只有环带轮廓那条线会跟着反相变**：α=0 时它反而是画满的）。
  灶膛**也不受**影响，始终是一块够暗的炭底（见 `CAMP_PIT_MIN_ALPHA`）—— 火是靠
  对比度被看见的，浅色桌面上没有暗底它就会"发灰、不亮"
- **底盘一透明，盘中央的文字就看不清了？**（用户第 8 轮报两件事：45% 时灰色盘面上
  的灰字和背景重合、0% 时白字被背景整个盖住）。文字一直是**直接用主题色画**的、
  没有自己的底色，底盘一透明它就贴在桌面上，对比度完全交给"桌面碰巧是什么色"。
  解法是给每段文字描一圈 1px 的**反相光晕**（`THEMES.text_halo`，dark 配暗边、light
  配亮边；实现在 `overlay._hud_text`：同一段文字按 8 个方向各偏移 1px 先铺一层反相色，
  再原位填真色）——**底色是深是浅、盘体透明与否都不影响**，反相那圈边总能勾出字形。
  **只在数字仪表盘模式**（篝火模式中心是火、没有文字）。逐组合实测见
  `_text_read_probe.py` → `_text_read_probe.png`（改前浅色桌面上白字 Δlum 低到
  2.0，改后最差也有 133）
- **篝火模式有暗盘芯、数字模式却悬空？**（用户第 14 轮："100% 透明度下篝火部分有
  深色背景、文字部分没有，有点割裂"）。根因：旧灶膛 `pit` 被 `if campfire:` 包着，
  数字模式根本不画中央底，而 `pit` 的 alpha 走 `CAMP_PIT_MIN_ALPHA`（232，约 91%
  不透明）—— 100% 透明时篝火模式仍是块近不透明暗盘，数字模式却啥都没有，对比即割裂。
  解法：给两个主题加 `THEMES.center_bg`（dark 与 `CAMP_PIT` 同色、light 用浅色
  `(236,238,243)` 让暗字压得住），中央盘改为**两种模式都无条件画**、按模式取色
  （篝火=`CAMP_PIT`、数字=`center_bg`），半径和灶膛一致。Qt 在 `paintEvent` 画、Tk
  把 `i_pit` 移出 `_camp_items` 做到两模式共用。逐模式对照见
  `_center_bg_probe.py` → `_center_bg_probe.png`（4 行 × 3 桌面，`bg_alpha=0`）
- **低热度的弧发糊？** 那不是色阶配错了。热度色阶的 0~45% 段是**等亮度变色相**
  的（冷蓝 → 青绿 → 草绿，亮度恒定在 141~150），所以只要轨道（未走段）漂到这个
  亮度附近，两者就糊成一片。轨道原来正是**半透明白**，浅色桌面 + `bg_alpha` 72%
  时能漂到 134 —— 正好撞上。现在 `THEMES.track` 是**定色不透明**
  （dark `#4A5261` / light `#C2C7D1`，与 Tk 版逐位相同），弧与轨道的亮度差恒定在
  ±60。**别把它改回带 alpha 的四元组** —— `_test_ring.py` 会红。逐组合实测见
  `_arc_contrast_probe.py` → `_arc_contrast.png`
- 觉得火太小/太大 → 调 `heat.full_kpm`：调小 = 同样的活动火更旺
- 不想统计鼠标（比如在用触控板容易误触）→ `mouse.enabled` 设 `false`，
  鼠标钩子完全不挂，零开销，热度只剩键盘
- 鼠标占比偏重/偏轻 → 调 `w_move`（移动权重）；调到 `0.002` 约等于 500 次移动 = 1 次击键
- 多显示器想放副屏 → `screen` 改成 1（**仅 PyQt6 版支持**，Tkinter 版固定主屏）

> **关于 `*` 前缀**：JSON 没有注释，所以这里约定 `"_key"` 放中文说明、`"*key"` 标记
> "这条该改"。读取代码认 `key` 和 `*key` 两种写法（`heatcore.cfg_get`），两种都能用。
> 之前踩过坑：代码只认 `size`，配置里写的是 `*size`，于是改了配置完全没反应、也不报错。

## 数据与隐私

**只有 7 列，落在本地，不联网：**

| 字段 | 含义 |
|---|---|
| `minute_ts` | 分钟时间戳 |
| `keystrokes` | 该分钟击键数 |
| `backspaces` | 该分钟退格/删除数 |
| `modifiers` | 该分钟修饰键数 |
| `active_secs` | 该分钟活跃秒数（键鼠任一有动作） |
| `mouse_moves` | 该分钟鼠标移动事件数 |
| `clicks` | 该分钟鼠标按下次数 |
| `scrolls` | 该分钟滚轮格数 |

**没有任何按键内容、窗口标题、进程名，也没有鼠标坐标。** 这条边界是写死在
`heatcore.py` 的 schema 里的，代码里没有开关 —— 不留"要不要记录内容"这个选项。

鼠标坐标只作为回调参数出现，随即丢弃，不进任何持久结构。键盘事件同理：只有
"是哪一类、发生在哪一分钟"这两个信息进入内存。

补出鼠标三列，历史数据原样保留、新列为 0。

数据库就是 `data/heat.db` 一个文件，删掉即清空。

写测试的配套工具（**断言有没有牙，靠它证明**）：

```bat
.pyenv\Scripts\python.exe _revcheck.py <源文件> <锚点片段> <测试脚本>
.pyenv\Scripts\python.exe _revcheck.py <源文件> "<锚点片段>=><替换文本>" <测试脚本>
:: 例：把内弧那行注掉，确认 _test_ring.py 真会红
.pyenv\Scripts\python.exe _revcheck.py overlay.py "path.arcTo(rect_i, end_deg, SWEEP_DEG)" _test_ring.py
:: 例：把反相公式换成旧行为（恒不透明），确认第 10 节的 11 条断言真会红
.pyenv\Scripts\python.exe _revcheck.py flame.py "return max(TRACK_EDGE_ALPHA_MIN, (1.0 - a) ** TRACK_EDGE_ALPHA_GAMMA)=>return 1.0" _test_ring.py
```

- **反向验证是硬要求**："改好了就绿"只说明两边一致，说明不了断言盯着那行代码。
  `_revcheck.py` 把"备份 → 注掉含锚点的那一行 → 跑测试 → 无论成败都还原"做成一条
  命令，锚点必须**唯一命中一行**（否则报错退出，宁可不动也不猜着注）。它把失败
  条目打出来，并在**全绿**时明确告诉你"断言是空转的，必须重写"。之前几轮都是手工
  改来改去，容易忘还原、也容易注错地方。
  **"注掉"和"换成旧行为"不是一回事**：注掉一行常常让测试直接抛异常（函数返回
  `None`、属性消失），那只证明"这行被引用了"，证明不了"断言盯着它的行为"。能用
  `=>` 换成旧行为就别只注掉 —— 换掉之后仍然全绿，才是真的空转。工具两种都支持
  （注掉多行语句的第一行会让测试直接抛异常而不是打 `[FAIL]`，工具会另外报出来，
  但要看一眼异常对不对路）

- `_test_single.py` 要求**先退掉正在运行的实例**，否则 `首次申请` 会失败
- `_test_flame.py` 是改篝火时的主力：几何、锚点、槽位、配色的**两端数值**都钉死
  在里面。断言要盯**性质**、别盯中间量 —— "满热形状/颜色写死"那类数值每轮调整都
  得跟着改，是负资产（已经换掉好几条了）。旺火那一端现在盯的是"中焰/焰芯逐位
  不变 + 外焰更亮 + 外焰仍比中焰暗（体积线索不许丢）"这种性质。**改柴堆大小时
  尤其要跑它**：起火点的相对高度是反推的（`flame_anchor_pos()`），柴堆一小就可能
  让满热火根戳出柴堆底边；这一点有贴图 / 无贴图两条路径都断言了，还带了
  d=120/190/240 的缩放不变性
- `_test_tray.py` 盯着 Qt 一条反直觉的行为：**`setCheckable(True)` 不带互斥**，
  单选菜单不配 `QActionGroup` 就会有两个对号。它直接调生产函数
  `overlay.build_choice_menu`（不是复刻一份），用 `QTest` 走**鼠标点击**和
  **键盘回车**两条真实路径，断言勾选数恰好 1；另有一组源码守卫，谁再手写一组
  单选就红。**反向验证过**：注掉 `group.addAction(act)` 立刻 9 条失败，勾选串
  `0011` / `1010` 正是用户看到的现象
- `_test_ring.py` 盯圆环（进度条）的可读性：**轨道必须是 alpha=255 的定色**，
  半透明就会跟着桌面漂、撞上低热度弧的亮度。主判据是"真实渲染结果里轨道像素的
  alpha 必须是 255" —— 这是根因，比对比度数字更直接。它还会读 `overlay_tk.py`
  源码、断言两版 track 逐位同色（防双 UI 配色分叉）。**反向验证过**：把 dark 的
  track 改回 `(255, 255, 255, 74)`，立刻 12 条红。
  第 5 节是"**底盘最外圈不许有描边线**"（用户报"圈圈最外面有一个白色的圆形线条"）：
  判据不用合成桌面 —— 底盘边缘的抗锯齿只是"plate 色 × 透明度"的混合，**不改变
  非预乘 RGB**，所以边缘那几行的颜色必须仍等于 plate（容差 10，留给预乘往返的
  舍入；描边混进来是 100+ 的量级）。边界位置不靠几何公式，而是"沿正下方（弧的
  缺口）扫，取最后一个 alpha ≥ 100 的像素"—— 实测窗口最后两行会有 `grab()` 的
  残留伪影（α=1）、越界像素返回 `(0,0,0,255)`，都躲开。**反向验证过**：把描边
  加回去，5 条红，边缘像素变成 `(194,196,196)` 这种亮灰。
  第 6 节是"**环带轮廓四条边都要找得到纯色像素**"：外弧和内弧各扫一小段窗口，
  断言存在一个像素**逐位等于** `THEMES.track_edge`；顺带盯几何（外弧 > 环外沿 >
  环内沿 > 内弧，端头半圆 = 两弧间距的一半）。这一节还**间接盯着灶膛的画序** ——
  灶膛半径和轮廓内弧只差 1.5px，灶膛要是画在轮廓之后，内弧就被切掉一截、
  挤不出纯色像素。**热度取 4%、α 取 0**：22% 时 180° 落在热度弧里，弧的内边缘
  和轮廓内弧只差 0.07px，抗锯齿会把线色渗成 `rgb(197,204,216)`（差 1 个单位）；
  α=0 那一档线才**画满**（见第 10 节的反相规则），α=72% 时只有 28% 不透明，
  **按定义**没有纯色像素。
  **反向验证过**：注掉 `path.arcTo(rect_i, ...)`，内沿 2 条红。
  第 7 节是"**轨道和底盘撞车时边界要分得开**"（用户报"透明度 72 时进度条
  底色和圆盘底色区分度太低"）。它和第 5 条禁的不是同一条线：第 5 条禁的是
  **盘子轮廓**上那条，这条在**环带外沿**（半径差 ~6px，互不重叠）。这节**必须把帧
  合成到桌面底**上再量 —— 底盘是半透明的，撞车是"底色 × 桌面"混合后才发生的，
  离屏帧上看不见桌面也就看不见撞车。量化时还有两个坑：① 细线在半径方向只有
  1px 实心、两侧是抗锯齿，**必须取单像素**（3×3 中位会把线抹成半价，连相对强弱
  都会看错）；② 判据是 **max(盘面自己 vs 轨道, 线自己的分离度)** —— 线的透明度
  反相以后，"线淡下去"和"盘面自己站起来"是同一枚硬币的两面，只盯线会误判
  （α=100% 那档线按设计就没画；28% 的线**按构造**也只能拉开约 1/4 的距离，
  所以门槛是 20 而不是定色线的 25）。
  第 8 节是"**端头（转角）也要有线**"（用户第 6 轮报"内圈和转角也应该有"）。
  量法：在环中心线处沿**切向**跨过弧末端（−40°）取剖面，找同时最远离轨道和底盘的
  像素，并断言最优点落在 **t>0（弧外、缺口那一侧）** —— 直线封口会落在 t=0，
  只有绕圆笔帽的半圆才落到 t>0。起点 220° 不列判据：它总被热度弧的圆笔帽盖着。
  **反向验证过**：注掉 `path.arcTo(rect_e, ...)`，4 条红（分离度从 117 掉到 1.6）。
  第 10 节是"**线的透明度与底盘反相**"（用户第 7 轮："它的透明度和整体的透明度是
  反着来的"）。四条一起查：① 公式本身（`1 − bg_alpha`、两个端点、单调）；
  ② 渲染对得上 —— α=0 时窗口里**找得到逐位等于 track_edge 的像素**，α=100% 时
  **窗口里没有任何像素靠近 track_edge**（线真的消失，不是"很淡"）；③ α=72% 时线
  的像素必须等于 `线色 × 28% + (底盘 × 72% 桌面)`，容差 5；④ 四档 × 三桌面全扫
  `max(盘面, 线) ≥ 20`。**反向验证过**：把公式换成 `return 1.0`，11 条红；把 Qt 的
  `setAlphaF` 换成 `1.0`，12 条红。
  第 9 节是源码守卫：底盘不许有描边、轮廓必须画在轨道之前、`QPainterPath` 那六行
  （外弧 / 末端半圆 / 内弧 / 起点半圆 / `closeSubpath`）一行都不许少、Tk 侧四个
  轮廓元素都先于 `i_track`

## 常见问题

**杀毒软件报警 / 提示键盘记录**
预期之内。`WH_KEYBOARD_LL` / `WH_MOUSE_LL` 这两个系统钩子本身就是键盘记录器、
鼠标监视器用的同一套 API，杀软只能按行为特征判断，看不出你的用途。加白名单即可。
介意的话把 `mouse.enabled` 设 `false` 少挂一个钩子，或用 `demo_data.py` 看报告。

**开机自启**
```powershell
powershell -ExecutionPolicy Bypass -File autostart.ps1          # 开启
powershell -ExecutionPolicy Bypass -File autostart.ps1 -Remove  # 关闭
```
走的是启动文件夹快捷方式（`shell:startup`），不是注册表，出问题肉眼可见、直接删。

**打包成单个 exe**（不依赖 Python 环境）
```bat
.pyenv\Scripts\python.exe build.py
```
产物名**带版本号**：`dist\键盘热度-v1.2.0.exe`。版本号只有一个来源 —— `version.py`
的 `VERSION`；`键盘热度.spec` 从那里取名字，托盘 tooltip 也显示同一份，所以
**文件名的版本和程序里显示的版本永远一致**。改版本只需改 `version.py` 一处。

`build.py` 还会自动把 `BUILD_DATE` 写成当天、并在打完时列出 `dist/` 全部产物及时间
（最新的标「本次打包」，旧的标「可回退」）。**不要删旧 exe**：文件名带版本号后它们
天然不会互相覆盖，新版有问题直接换回旧版即可。

> 为什么坚持带版本号：开发期反复打包，旧产物可能带已知缺陷 —— 2026-10-15之前
> 那份一旦双击就 `0xC0000409` 秒退（原生层崩溃，`error.log` 都不会有记录），
> 文件名不带版本时根本分不清手上跑的是哪一份。

底层命令（`build.py` 就是它的一次包装，正常用 `build.py` 即可）：
```bat
.pyenv\Scripts\python.exe -m PyInstaller --noconfirm 键盘热度.spec
```

**双击了但没反应 / 看不到悬浮窗**
按这个顺序查，基本一步定位：
1. **看 `_launch.log`** —— `run.bat` 每走一步都会写一行。最后一行是什么，就卡在哪：
   - 没有这个文件 → bat 根本没被执行（双击的是别的文件，或安全策略拦了 .bat）
   - `runtime MISSING` → `.pyenv` 丢了，跑 `install.bat`
   - `launched` 但没有窗口 → 那是程序层的问题，看第 3 条
2. **改用 `launch.vbs`** —— 它绕开 cmd.exe。能起来就说明是 bat 解析的问题
3. **带控制台启动直接看报错**：`.pyenv\Scripts\python.exe main.py`（不要用 `pythonw`）
4. 看 `data/error.log` 有没有堆栈（`main.py` 顶层异常会写这里）
5. 旧实例还活着时，新实例会叠在同一位置，先 `Ctrl+Alt+Q` 把旧的退掉

**程序在跑，但圆盘"看不清"**
实测踩到过：深色底盘 + 低不透明度叠在深色终端/壁纸上会整块糊进背景。
启动时还有一圈扫光报到；另外**底盘外沿那道 2px 描边已经去掉**（用户要求，见
`config` 那节），所以现在轮廓**只靠盘面自身与桌面的色差**，深色桌面上会更淡。若还
觉得不够：
- `overlay.theme` 换成 `light` —— 白底盘在深色终端上对比度最强（浅色桌面反之用 `dark`）
- 或把 `THEMES.dark.plate` 往亮里调一两档（默认 (24,27,35) 与深色终端桌面 (30,30,36)
  只差一点，去掉描边后两者基本连成一片）
- `overlay.bg_alpha` 提到 `0.88` 以上（越接近 255 越接近纯盘面色，越不受桌面影响）
- **圆环不用跟着调**：轨道（未走段）和进度弧都是定色不透明的，`bg_alpha` 调到 0
  也读得出来。底盘糊不糊和进度条清不清楚是两条独立的线 —— 原先不是这样：
  半透明的轨道会漂到低热度弧的亮度上糊成一片，已修（见 `config` 那节最后一条）

**篝火看着"发灰、不亮"（像加了层遮罩）**
先别去调火焰配色 —— 八成是**灶膛底不够暗**。火是靠和背景的**对比度**被看见的，
不是靠自身颜色有多亮。半透明的灶膛在浅色桌面上会被白色冲淡成中灰：实测白色桌面
(255,255,255) 上，`CAMP_PIT_MIN_ALPHA=96` 时灶膛合成出来是 rgb(164,164,165)，
比空闲火焰 rgb(189,86,0) 的亮度还高 77 —— 于是整簇火"发闷"，光晕（加法混合）
叠在亮底上只会更白，等于白画。用户的直觉是"是不是加遮罩了"，机制其实**反过来**：
不是加了暗遮罩，是灶膛太透、桌面透上来了。

现在的值 232 在白底上合成出 rgb(36,34,38)，比空闲焰芯暗一档。自己验：
`.pyenv\Scripts\python.exe _backdrop_probe.py` —— 它抓真实桌面当底，扫描灶膛
不透明度并输出对照图。想确认"是不是真有遮罩"：
`.pyenv\Scripts\python.exe _screen_probe.py` —— 离屏绘制像素 vs 真实屏幕像素逐点
对拍，两者一致就说明合成层是干净的，问题必然在配色/底色。

**改了 `config.json` 没反应**
确认改的是 `*` 开头的那个名字。现在两种写法都认（`cfg_get`），但如果你在配置里同时
写了 `size` 和 `*size`，**不带星号的那个优先**。改完必须重启程序。

**重复双击会怎样**
有单实例保护：不会叠出好几个圆盘，而是弹一个置顶提示告诉你窗口在哪、怎么调清晰。

**鼠标活动量看起来大得离谱**
正常。移动事件是像素级的，一次划屏就能产生几百上千次。所以它在折算里只占 0.01 ——
报告里"鼠标移动 13.2万 次"听着吓人，折算后其实相当于 1320 次击键。

**Tkinter 版报 `No module named 'tkinter'`**
`install.bat` 会优先挑自带 tkinter 的解释器（本机是
